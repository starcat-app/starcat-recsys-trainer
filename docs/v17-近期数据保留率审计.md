# v17 近期数据保留率审计

> 审计日期：2026-11-03。范围：只读诊断既有数据，不修改训练规则、不重训或切换模型。

## 1. 结论

近期评估样本稀少由三类因素叠加，不能归结为一个“模型没训练好”的问题：

1. 本地 Raw 的近期输入本来就少；Raw → Canonical 的计数未出现额外损失。
2. 历史头部仓库目录、训练期支持度、2% 主体抽样和参考目录主体准入继续收缩样本。
3. 存在独立的数据正确性问题：相同 WatchEvent ID 在本地不同年份对应不同事件，
   当前只按 `source + source_record_id` 去重，会让新事件覆盖不相关的历史事件。

第三项需要修复，但不能据此断言它单独造成了 v17 指标下降；本轮没有修改规则后重新
评估，也没有证明 Raw 的近期下降是上游变化还是下载结果不完整。

## 3. 10 月逐层保留量

| 处理阶段 | 剩余记录 | 本阶段减少 |
|---|---:|---:|
| Raw / Canonical | 241,782 | — |
| 仓库在已有 metadata 目录中 | 53,189 | 188,593 |
| 公开、未归档、未 disabled | 52,962 | 227 |
| 现有事件 ID 去重 | 52,959 | 3 |
| 仓库满足训练期支持度等有效目录条件 | 46,557 | 6,402 |
| 稳定 2% 主体抽样 | 990 | 45,567 |
| 同一来源主体—仓库只保留首次 Star | 888 | 102 |
| 参考目录训练期计数在 5～200 | 291 | 597 |

最终为 274 个主体、247 个仓库，保留约 0.12% 的原始事件行。
2% 是主体抽样，不是每个月严格保留 2% 行数。首次 Star 去重与事件 ID 去重也是
两种不同操作：前者合并同一主体对同一仓库的多次事件，后者当前有身份冲突问题。

在最后 888 条近期唯一关系中，557 条因参考目录训练期仓库数不足 5 被排除，
40 条因超过 200 被排除。此准入只允许在旧参考目录已有一定历史的主体；它有助于
控制旧实验的混杂，但不代表所有近期用户，更不覆盖完整冷启动人群。

### 仓库目录不是近期全量目录

Canonical 当前 metadata 有 14,734 个仓库，公开且活跃为 13,640 个，最终有效目录
为 13,638 个。代码通过全时段行为 `count(*) DESC` 取前 15,000 个 ID 后补 metadata，
不是按近期热度或全部公开仓库覆盖；10 月 99,280 个出现过的 repo ID 中只有 6,504 个
命中当前 metadata。因此“训练配置允许 15,000”不等于已覆盖近期仓库。

10 月支持度过滤丢掉的 6,402 条来自公开目录中的 `morluto/rea`。其 Canonical 共 6,405 条，
在 2026-09-01 训练截止前只有 1 条、1 个主体，确实达不到 20 个主体的门槛。
不能为了补 test 数量把 test 行为倒灌成训练支持度；这是需要单列的仓库冷启动问题。

## 4. 事件身份冲突与时间隔离风险

调用链：

- `sources/bigquery.py` 将原始 `id` 转为 `source_record_id`。
- `canonical.py` 原样保留该 ID，主体作来源隔离的 SHA-256，`observed_at=created_at`。
- `dataset.py` 在时间切分之前，按 `source, source_record_id` 分组，取 `observed_at DESC`
  的第一条；相同 ID 的不同年份事件因此会互相覆盖。

在“2026 年命中公开活跃目录的事件 ID”及其全部年份竞争记录中：

| 检查项 | 数量 |
|---|---:|
| 存在重复记录的 ID 组 | 22,914 |
| 其中主体、仓库或时间不同的冲突组 | 22,885 |
| 跨年份 ID 组 | 22,885 |
| 被覆盖的不同历史事件 | 22,886 |
| 其中训练期事件被 validation / test 期事件覆盖 | 1,017 |

上述是本次近期 ID 范围内的统计，不是完整十年全量冲突审计；也没有全局推断 GitHub
ID 规则发生了什么变化。抽取一组冲突，只读取其两个 Raw 日分区后确认：
2017-03-25 与 2026-01-01 的相同 ID 对应两条不同主体、不同仓库、不同时间的事件。
因此不能把问题归因于 Canonical 后来重新生成了相同 ID。

当前规则对近期记录的直接删除很少，10 月仅 3 条，远小于目录和抽样损失。
但较新的无关事件能删除训练期历史，构成时间隔离风险；这属于正确性修复，
不能以这次损失比例小为由保留。反之，修复后有多少评估收益仍须重新验证，不能预承诺。

## 5. 验证、限制与产物

分阶段审计使用固定 6 GiB / 单线程，临时表和 spill 与原 run 隔离，仅输出聚合数据。
没有在报告或控制台输出主体、原始事件 ID、凭据或真实训练根路径。

第一轮主体历史追溯发现：若在抽样后才做事件去重，会漏掉未抽样主体对相同 ID 的竞争，
有 149 条局部赢家与全局赢家不同。虽然分月计数与既有 Dataset 一致，仍不能把该近似
重放称为逐行等价。因此另行查询全部相关 ID 的全局竞争记录，先确定全局赢家，再应用
有效目录和抽样，完成精确重放：

- 复算 Dataset 共 2,061,640 行，与既有产物总数一致。
- 2026 年近期事件的来源、主体、repo ID、事件 ID 和时间元组，双向集合差异均为 0。
- 10 月抽样后 990 条、首次关系 888 条及准入的 557 / 291 / 40 分解再次一致。
- 相关历史 ID 没有同一 `observed_at` 下的不同语义竞争，因此此重放没有用任意排序
  掩盖该范围内的同时间平局。

复核结果单独归档在 `cohort-exact-summary.json`，不使用局部重放替代产品语义。

审计目录标识为 `gharchive-v17-audit-20261103`，包含输入检查、分阶段保留量和精确
重放的 JSON。
诊断脚本随该目录归档，只读既有输入，不写 Raw、Canonical、Dataset 或 Registry。

## 6. 后续建议，尚未实施

1. 先修复 WatchEvent 的事件身份：不能仅假设 ID 全局唯一，应保留时间、主体、仓库
   不同的真实事件；完全相同的重复记录仍合并。其他数据源及最新快照语义不顺带改动。
   增加跨年份同 ID、完全重复、未来事件不能改变训练历史等回归测试。
2. 对近期异常低量日期做限定预算的上游行数对账，再决定是否需要重新下载；
   不先盲目重下十年数据，也不在没有授权时运行收费查询。
3. 重新制定训练与评估抽样协议：不要把训练的 2% 资源限制直接当成评估人群限制，
   单列旧目录、近期活跃、用户与仓库冷启动切片；所有采样和目录选择只用可用训练期信息。
4. 数据正确后再建独立版本 Dataset，冻结选型与留出规则后训练。已观察过的 10 月成绩
   可作回归参考，不再称完全未知的最终 test。修复本身不自动授权模型激活或部署。

本轮只确认审计结论；没有修改训练业务代码、重训、下载、执行 BigQuery、提交、推送、
部署，也没有写功能总览或 Changelog。活动 Registry 仍为既有 v16。
