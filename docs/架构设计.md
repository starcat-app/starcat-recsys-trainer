# 架构设计

## 1. 职责

本项目负责推荐数据采集、标准化、训练、评估和产物发布，不承担公网在线查询。长期统一在线服务 `starcat-recommend-api` 通过 `/api/v2` 读取 ServingBundle；`/api/v1` 继续使用 SimRepo。

## 2. 数据分层

```text
raw        原始来源数据，只做不可变落地和 lineage
canonical  InteractionRecord / RepositoryRecord
dataset    train / validation / test 与统计信息
model      训练器输出、指标和 model manifest
published  可原子切换和回滚的 ServingBundle
```

## 3. 数据来源

| Connector | 模式 | 职责 |
|---|---|---|
| `BigQueryWatchEventSource` | Pull | 从 GH Archive 显式 UTC 日表导入公开 WatchEvent |
| `BigQueryPushEventSource` | Pull | 从 GH Archive 显式 UTC 日表导入五字段精简 PushEvent |
| `BigQueryPushEventMetadataSource` | Pull | 从 GH Archive 年表批量聚合仓库 ID、最新名称和 Push 时间范围 |
| `GitHubRepositoryMetadataSource` | Pull | 根据 repo ID 补齐公开 metadata |
| `StarcatSnapshotSource` | Push landing reader | 读取 Starcat 匿名公开 Star 完整快照 |
| `StarcatCollectionAPISource` | Pull | 用 Admin Key 拉取 Collection active 快照导出，校验 checksum 后落入 raw |
| `LocalFileSource` | Local import | 重放已落地 raw 分区和本地验收 fixture |
| `LocalLakePartitionSource` | Local reference | 按 checkpoint 只读登记已有 WatchEvent / PushEvent 日分区，不复制 Raw |

GitHub Stargazer 列表不作为第一版公共行为来源。GitHub 已限制该接口的公开访问，GitHub Connector 主要负责仓库 metadata。

GH Archive 的 `day` dataset 同时包含 `yesterday` View，不能使用 `githubarchive.day.*` 通配查询。Connector 将经过严格校验的 `YYYYMMDD` 日期映射为 `githubarchive.day.YYYYMMDD` 显式表名，每日先 dry run，再以相同 SQL 和 `maximum_bytes_billed` 执行正式查询。

WatchEvent 与精简 PushEvent 长时间窗口通过两个独立 CLI 先落入各自的可复用 raw zone。每个日分区先写入同目录临时 Parquet，完成后原子替换，再把 SHA-256、行数和预计扫描量写入各自的 `download-state.json`。恢复时同时校验 Parquet footer、字段和 checksum；校验通过的日期不再访问 BigQuery，损坏分区才重新下载。首次全量完成后，`--append-existing` 只校验请求日期并连续推进同一个 checkpoint，不重扫历史 Raw；跳日或改变预算、Location、`run_id` 会被拒绝。每日预算由 BigQuery `maximum_bytes_billed` 执行，累计预算由 Connector 在每次正式查询前执行。只有限流、服务不可用、网关超时等瞬时 Google API 错误使用指数退避重试，权限、SQL 和预算错误立即终止。

WatchEvent 的日常入口 `download-watch-events.sh catch-up` 从 checkpoint 计算最后连续分区，
默认同步追到最新完整 UTC 日。日期规划与下载解耦：规划阶段发现缺口、UTC 当天目标或损坏状态
会直接失败；执行阶段仍复用同一预算、原子 checkpoint 和断点恢复语义。

该入口只推进 Raw 下载事实，不推进 History Silver、Delta 或生产 `active_watermark`。生产每日链路
由 Starcat 主仓库 `supports/scripts/run-history-daily-sync.sh` 串联：先等待 `catch-up` 成功，再让
History Builder 从云端水位逐日消费 Raw。四层事实分别记录，不能用 Raw 文件存在推断发布完成：

```text
Raw completed partition
  -> History Silver source_watermark
  -> History Delta (from_watermark, to_watermark]
  -> Production active_watermark
```

完整运维契约见
[WatchEvent 与 Star History 每日增量运维指南](../../../docs/2-产品/需求讨论/推荐算法/WatchEvent与Star-History每日增量运维指南.md)。

两个后台任务使用独立 `screen + caffeinate` 生命周期和 checkpoint，但共享同一 GCP Project 的月度额度边界。各自启动时以及默认每 30 分钟查询一次区域级 `INFORMATION_SCHEMA.JOBS_BY_PROJECT`，把本月 `total_bytes_billed` 写入日志；达到 80% 记录警告，达到 90% 向对应下载进程发送终止信号。该统计只覆盖配置 Project；若同一 billing account 还绑定其他 Project，应以 Cloud Billing 报表作为最终口径。

`lake inspect-watch-events` 与 `lake inspect-push-events` 是 Catalog 登记前的只读适配层。它们以
checkpoint 的任务范围和完成分区为入口，重新校验 Parquet footer、固定字段、行数和 SHA-256，
同时把尚未下载的预期日期明确输出为 missing。结果只使用稳定 Dataset ID 与逻辑 URI，不输出
管理员用户名、磁盘名称或真实绝对路径；扫描期间不会移动、复制或改写正在下载的 Raw。

PushEvent metadata 使用 `githubarchive.year.*` 和严格校验的四位年份后缀，一次聚合每个 repo ID 的最新名称、首次/末次观察到的 Push 时间和事件数。它是扩大候选目录的低成本基础层，不代表仓库真实创建时间或当前完整状态。Canonical 给它较低的 `metadata_version`；GitHub API 的当前名称、描述、Topics、语言、License、Star/Fork 数和 archived/disabled/visibility 状态始终优先。

## 4. 标准数据模型

行为关系和仓库特征使用不同模型。GH Archive 的 `star_event` 与 Starcat 的 `current_star_membership` 保留各自语义，不通过真实 GitHub 身份跨来源连接。

## 5. 数据质量与切分

- Starcat 完整快照对每个 source-local subject 只保留 `observed_at` 最新的一版。
- 互动先按 `(source, source_record_id)` 去重，再按 source-local `(source, source_subject_id, repo_id)` 统一为一条隐式反馈；GH Archive 重复 WatchEvent 取首次事件，不尝试跨源合并主体。
- 只保留 metadata 为 public、未 archived、未 disabled 的仓库。
- 可按 `train_end` 前去重后的正向主体数过滤低支持度仓库；该值是训练窗口内观察到的 Star/贡献主体数，不冒充 GitHub 当前 `stargazers_count`，validation/test 不能改变该阈值结果。
- 可配置主体最少和最多仓库数，隔离信号不足以及疑似机器人/采集账号的超大集合。
- 可按训练窗口支持度保留 Top N 仓库，并对 source-local subject 做稳定哈希抽样；全量 Raw 仍参与扫描、记录去重和仓库支持度统计，稳定抽样在昂贵的主体-仓库聚合前应用，只有进入单机模型的数据集被收敛。
- 训练资格只根据 train cutoff 前的 repo 数计算；少于 2 个 train repo 的主体不参与训练，但可保留 train history 参与 validation/test 评估。
- 主体权重为 `source_weight / log2(2 + train_repo_count)`，validation/test 行不能改变训练权重。
- `occurred_at < train_end` 进 train，介于 `train_end` 和 `validation_end` 进 validation，其余进 test。缺少 `occurred_at` 的旧快照只进 train。

## 6. 训练与评估

Popular、TruncatedSVD 和 co-star 都只读取 `split='train' AND training_eligible`。Popular 使用 train catalog 的加权互动量；TruncatedSVD 对稀疏 subject-repo 矩阵分解并以 item embedding cosine 构建近邻。

候选模型的样本条件彼此独立。当前授权数据只有一个主体时，SVD 无法形成可分解的主体维度，执行器将该节点记录为 `skipped` 并保留原因；Popular、co-star、评估和所选模型发布继续执行。只有明确的 `InsufficientTrainingDataError` 可以降级，其它训练异常仍立即终止管道。

co-star 使用以下公式：

```text
time_weight = exp(-ln(2) * age_days / half_life_days)
missing occurred_at => legacy_time_weight

support(i, j) = Σ subject_weight * min(time_weight_i, time_weight_j)
cosine(i, j) = support(i, j) / sqrt(support(i, i) * support(j, j))
score(i, j) = cosine(i, j) * support(i, j) / (support(i, j) + shrinkage)
```

为避免超大 Star 集合产生无界 pair，每个主体最多使用 `maximum_repositories_per_subject` 个时间权重最高的仓库，并以稳定主体哈希顺序把实际 pair 展开量限制在 `maximum_pair_observations` 内。该上限只影响 pair 训练，不删除 raw 或 canonical 数据。Popular 只与全局 Top-K+1 热门仓库做小表交叉；三个 SQL 模型产物均由 DuckDB 直接写 Parquet。

SVD 在 DuckDB 内依次限制仓库、主体和非零项，再分批填充 SciPy CSR；item 近邻按 `neighbor_batch_size` 分批计算和写 Parquet。评估只选择稳定哈希顺序的有界主体并仅读取这些主体涉及的模型边。Bundle 通过 Parquet batch 追加 SQLite，不整表 `to_pylist()`。

所有生产训练节点都通过统一连接工厂创建 DuckDB。连接内存上限固定为 6 GiB、线程数固定为 1，并关闭不影响查询语义的 insertion-order preservation；这是 64 GiB M2 Ultra 对 5.1 亿条 Canonical 的实测稳定下限，4 GiB 无法完成聚合，8 GiB 并行配置会扩大 macOS swap。排序、聚合和窗口函数需要 spill 时，临时文件固定写入当前 run 的 `workspace/duckdb-temp/<task>/`，不能回落到 macOS 系统临时目录。因此只要训练 workspace 位于 T0，Raw、Canonical、模型和 DuckDB 临时数据就全部留在 T0。

离线评估以每个主体的 train repos 为 seeds，累加 item-to-item 分数预测 validation/test 目标，输出 Recall@K、NDCG@K、MRR@K 和 Coverage。Coverage 分母只使用训练资格有效的 train catalog，不受 validation/test 首次 repo 影响。`training.reference_time` 必须等于 `dataset.train_end`；`run_ablations=true` 时额外训练 no-decay 和 no-shrinkage 变体。

当前实现是独立离线基线，只包含 Popular、TruncatedSVD 和 co-star。权威目标设计中的 Metric Learning、内容向量、动态融合、元数据校正和 MMR 属于后续阶段，不应把当前基线描述为完整混合推荐模型。

## 7. 执行模型

第一版使用 `LocalExecutor`。所有节点通过 artifact URI、checksum 和 manifest 连接，不依赖同一进程内存。未来增加远程 worker、S3/MinIO 和任务租约时，不修改数据源、训练器和评估器。

Apple Silicon 多机第一阶段采用任务级并行，不实现跨多台 Mac 的 MPS 同步梯度训练。

YAML 管道先采集行为来源和 PushEvent 基础目录。Collection Connector 是唯一主动方：它访问受 Admin Key 保护的内部导出，Collection 服务不主动连接 Mac 或 Trainer。导出落地后只保留已 HMAC 的 source-local subject ID。当 `github_api.repo_ids_from_canonical=true` 时，管道按 canonical 行为量选取有上限的 repo IDs，延迟补齐权威 metadata，再增量合并仓库 Canonical；既避免对数百万仓库逐个调用 GitHub API，也不会再次扫描 WatchEvent。

长任务后半段失败时，可以用 `resume_canonical_manifest` 显式引用上一 run 的 Canonical manifest。新 run 会逐文件重算 SHA-256、校验 interactions/repositories 类型完整性，并写入 `canonical-resume.json` 记录来源；校验通过后直接从 Dataset 继续，不复制数十 GiB Canonical，也不重新查询 BigQuery 或 GitHub。新的 `run_id` 和 Registry 版本仍不可覆盖。

超过数天的首次 WatchEvent / PushEvent 采集不直接绑定后续训练任务：分别由 `bigquery download-watch-events` 和 `bigquery download-push-events` 完成可恢复 raw 下载，再把已校验分区交给后续处理。这样网络中断只重试未完成日期，不会因为下游训练失败而重复消耗查询额度。

## 8. 发布边界

ServingBundle 包含预计算 Top-K、公开 repo metadata、模型版本、信号、原因和 checksum。在线 API 只读该产物，不读取原始匿名快照或训练 subject。

Registry 以 `versions/<model_version>/` 保存不可覆盖的 Bundle，`active.json` 是可原子切换的激活指针。发布前必须通过指标门禁、文件 checksum 和 SQLite `quick_check`。

YAML 的 `publish.recommend_api` 为可选交付节点。它只接收本地 Registry 已安装的 `serving_bundle` artifact，把三个白名单文件压缩后通过独立 Publish Key 上传；Recommend API 再次校验 checksum、manifest、SQLite 和 schema 后原子激活。远端发布失败不会覆盖本地 Bundle，也不会产生伪造的成功回执。
