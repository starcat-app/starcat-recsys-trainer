# v18 事件身份修复与评估抽样方案

> 日期：2026-11-03。代码修复、质量门禁和独立 Dataset 重建核对均已通过。
> 本轮不训练模型、不生成 Bundle、不切换 active；抽样调整仅形成后续方案。

## 1. 为什么先修数据

[v17 审计](v17-近期数据保留率审计.md)已在 Canonical 及抽查的 Raw 中确认：不同年份的
WatchEvent 可以复用原始 ID。仅按 `source + source_record_id` 取最新观测，会把无关的
历史 Star 删除；其中一些训练期事件会被验证或测试期事件覆盖。

这是事件身份错误，不是模型超参数问题。修复不能承诺提升推荐指标，也不能把恢复
记录数量等同于恢复相同数量的训练关系：后续还有首次 Star、主体准入和目录筛选。

## 2. 已实施的最小修复

仅对 `source=gh_archive` 且 `relation_type=star_event` 使用以下事件去重身份：

```text
source + source_record_id + source_subject_id + repo_id + occurred_at
```

- 主体、仓库或事件时间不同的记录不再互相覆盖，包括相同时间但主体或仓库不同的情况。
- 同一事件的重复下载、重试仍合并；存在多次观测时保留 `observed_at` 最新记录。
- 不改其他来源的 ID 去重，不改 Starcat 的最新快照选择。
- 不改后续 `source + source_subject_id + repo_id` 首次 Star 聚合。
- 不改仓库支持度、主体 5～200 门槛、权重公式、2% 稳定抽样或时间切分。
- 不需要重建 Raw 或 Canonical，已有 Canonical 已保留上述字段。

`dataset.py` 在 Dataset Artifact 和质量报告中写入
`event_identity_policy=gh_archive_watch_event_v2`。这是产物溯源标记，不是让线上
长期维持两套去重算法的配置开关；旧产物不覆盖，新任务使用独立 run_id。

### 回归验证

新增 7 个参数展开后的测试用例，覆盖：

1. 同 ID、不同年份事件时间。
2. 同 ID、同事件时间但主体不同。
3. 同 ID、同事件时间但仓库不同。
4. 完全重复与同一事件的更新观测仍合并。
5. 加入未来无关同 ID 事件，不改变训练历史、目录支持度、准入或权重。
6. Starcat 最新快照和 ID 去重保持不变。
7. 其他来源即使产生 Star 关系，也不被套用 GH Archive 的新身份。

修改前前三项及未来事件测试失败，修改后完整 `make check` 通过：155 项测试、Ruff
格式与 lint、mypy strict，覆盖率 88%。没有仅凭新增测试通过替代完整门禁。

## 3. 独立 Dataset 对照

任务标识：`gharchive-20261031-v18-event-identity`。这里只把 v18 用作数据修复任务
标识，不代表已经训练或发布了 v18 模型。

| 项目 | 固定值 |
|---|---|
| Canonical | 复用 v16 固定输入，共 511,284,530 条，截止 2026-10-31 |
| 参考目录 | v15 已有仓库目录，只读 repo ID |
| train 截止 | 2026-09-01 00:00 UTC，左闭右开 |
| validation 截止 | 2026-10-01 00:00 UTC，左闭右开 |
| 主体准入 | 参考目录内训练期仓库数 5～200 |
| 仓库支持度 | 至少 20 个训练期主体 |
| 目录上限 | 15,000 |
| 主体稳定抽样 | 2% |
| 主体准入与权重 | `freeze_cohort=true` |
| DuckDB | 6 GiB、单线程，spill 在本任务外置盘目录隔离 |

与 v17 使用同一份参数，仅改变事件去重身份。开始前已逐文件重新计算并核对
Canonical SHA-256，记录参考目录、旧 Dataset、源码和锁文件摘要；不将已到
2026-11-01 的 Raw 增量悄悄混进来。执行器只调用 `DuckDBDatasetBuilder`，不调用
完整训练管道。

任务目录保存 `input-manifest.json`、`dataset/manifest.json`、质量报告、
`comparison.json`、`result.json` 和 `reproduction/`。前后核对 Registry active 摘要。
复现文件和本机路径只保留在本地数据目录，不在公开文档记录主体、事件原值或真实根路径。

重建后的核对范围：

- train / validation / test 的记录、主体、仓库数及 2026 年逐月变化。
- 新增与移除的完整事件身份、主体准入变化、目录支持度变化和权重变化。
- 同主体仓库仍无重复、事件未重复膨胀、首次 Star 恢复、参考目录准入及权重不变式。
- 新旧差异不能简单解释为审计中的 22,886 条：该数字仅覆盖近期 ID 的历史竞争，
  本次正式构建覆盖全部固定输入，且后续筛选存在级联影响。

### 重建结果

| 指标 | v17 | 修复后 | 变化 |
|---|---:|---:|---:|
| 公开活跃目录内原始互动 | 162,801,896 | 162,801,896 | 0 |
| 事件去重后 | 162,760,185 | 162,793,394 | +33,209 |
| 有效目录内、2% 主体抽样后 | 3,249,165 | 3,249,813 | +648 |
| 同主体仓库首次 Star 后 | 3,088,140 | 3,088,753 | +613 |
| 最终 Dataset | 2,061,640 | 2,061,840 | +200 |
| train | 2,059,869 | 2,060,069 | +200 |
| validation | 1,480 | 1,480 | 0 |
| test | 291 | 291 | 0 |
| 有效主体 | 59,934 | 59,940 | +6 |
| 候选目录仓库 | 13,638 | 13,638 | 0 |

完整输入范围内，原规则把 41,711 条记录当重复；新规则仅合并 8,502 条同一事件的
重复记录。33,209 是事件层恢复量，不是最终训练关系新增量，也不是上次仅检查近期 ID
所得到的 22,886 条历史冲突的简单重复统计。

目录没有新增或移除仓库，但 6,919 个仓库的训练期支持数改变，累计恢复 31,188 个
训练期主体—仓库支持计数；支持度仍只用训练截止前行为。

最终净增 200 条的分解：

- 7 个新准入主体带来 51 条关系。
- 仍在两版共同人群内的主体恢复 417 条关系，没有丢失已有主体—仓库对。
- 1 个主体的参考目录内训练期仓库数从 200 恢复到 201，被现有上限规则排除，减少
  268 条关系；已针对该主体重新只读核对固定 Canonical，不为保留它调整既有门槛。
- 共同关系中有 12 条恢复为更早的首次 Star，完整事件身份上各替换 12 条，净行数为 0。
- 因而是 `51 + 417 - 268 = 200`，不是只追加 200 条而其余记录逐字不变。

完整事件身份差异为训练集新增 480、移除 280；2026 年各月记录数及 validation / test
事件身份集合不变。不过历史恢复使 30,110 条共同关系的权重变化，其中 train 30,103、
validation 5、test 2；这是参考目录训练期计数恢复后的重新计算，并非权重公式改动。
不能把“留出行数不变”写成整个留出产物完全未变。

同主体仓库重复数、重复事件数、主体准入违规数和权重不变式违规数均为 0。
源代码摘要未变，Registry active 前后摘要一致，活动模型仍是 v16。重建约 23 分钟，
没有执行模型训练或生成新的推荐质量指标。

独立比较脚本最初使用了 DuckDB 保留字作为未加引号的别名，Dataset 已落盘后核对阶段
报语法错误。修正并用微型合成产物验证全部核对 SQL 后，校验已有产物 checksum 并
恢复核对，没有重复构建或训练。原始状态、原复现文件及修正版分别保留，最终
`result.json` 记录 `completed=true`、`comparison_resumed=true`。

## 4. 后续评估抽样方案，尚未实施

### 4.1 将训练预算与评估人群拆开

目前 Evaluator 从训练 Dataset 读取历史与标签；Dataset 已受 2% 主体抽样和参考目录
准入限制，后续提高 `maximum_subjects` 也不能找回已丢失主体。因此不能只把 Evaluator
上限从 10,000 调大。

后续增加独立的 evaluation Artifact，复用同一事件身份修复结果和时间切分：

- 训练仍可用 2% 稳定主体样本，单独记录训练主体数及配对预算。
- 评估从完整候选主体池独立选择，不要求命中训练 2%；只物化入选主体的 seeds 和标签，
  不把完整十年全量主体直接塞入 Python 内存。
- 分别冻结训练主体内评估与训练主体外评估，使用来源隔离的身份，记录交集数量；
  item-to-item 可用未参加训练主体的已知仓库历史推荐，但不能混称原人群回归。
- 同轮模型严格共享评估主体、历史、标签和候选目录，保持配对比较；不让各模型自行
  丢弃无结果主体，也不按模型是否命中筛选样本。
- 抽样盐、哈希规则、配额、过滤顺序、时间边界及 Artifact SHA 在看模型成绩前冻结。

这需要修改 Dataset / Evaluator 的输入契约及测试，尚未在本轮实现。

### 4.2 固定主指标人群，单列冷启动

| 切片 | 定义与用途 |
|---|---|
| 既有人群回归 | 固定参考目录计数规则，观察老用户场景，不当成完整用户总体 |
| 暖启动主指标 | 训练期已有 5～200 个可用仓库，独立于训练 2% 抽样 |
| 少历史主体 | 训练期仅 1～4 个可用仓库，单列，不偷偷并入既有主指标 |
| 无历史主体 | 无可用 seed；本轮 co-star 不支持个性化，单报比例，不虚构排序成绩 |
| 新仓库 / 目录外标签 | 训练期未见、支持不足或目录未覆盖；报告端到端损失，不倒灌标签扩目录 |
| 仓库长尾与近期主体 | 按训练期支持度及训练截止前近期活跃度划分，不能按测试热度分桶 |

主指标与各切片报告样本数、seed/标签数分布、空结果率、Recall@20、NDCG@20、MRR@20
和推荐覆盖率。标签至少有两种口径：

1. 端到端：真实符合公开数据边界的后续 Star，目录外标签仍计未命中。
2. 可推荐目录内：仅用于分解排序能力，必须同时报告目录覆盖率及被排除标签数。

不能仅展示第二种较好成绩。可按留出窗口存在正样本定义可计算人群，但须报告从预先
冻结主体池到可计算人群的流失；不得依据模型表现或后验人群调配额。

### 4.3 先做容量盘点，再冻结人数和精度门禁

建议首轮主指标上限仍为 10,000 个主体，目标不少于 5,000 个可计算主体；这只是待确认
的运行与精度目标，不是本轮已达成的数量，也不是数据不足时允许补入未来样本的理由。

先做不运行模型的主体与标签盘点，按训练期历史量分层（5～20、21～50、51～200），
固定每层抽样及聚合方式。若非等比例抽样，主总体指标需按预设总体权重还原，同时
保留各层配对指标，避免超采样后的简单平均冒充自然总体。

若不足目标或置信区间过宽，明确“证据不足”，在看成绩前决定延长观察期或扩大
独立评估抽样池；不再次降低 support 来凑样本，不把已看过的测试反复用作调参集。
对 Recall / NDCG 的模型差异使用同主体配对置信区间，并预先冻结允许退化范围。

### 4.4 时间、目录和参数隔离

- 候选目录的仓库入选、支持度、主体历史、权重及活跃度均只用训练截止前行为。
  当前目录来自事后 metadata 快照，存在可见性与存活偏差，必须标注回溯评估限制；
  后续目录选择不再用整个留出期热度决定 Top N。
- 推荐器 baseline 和候选都要在修复后的同输入、同切分上重训；旧缺陷模型仅作历史
  参考，不能把“修 bug + 换目录 + 调支持度”混成一个算法收益。
- 已观察过的 2026 年 10 月只作回归 / 开发证据，不再称未知最终 test。
- 真正的放行需要先锁定协议和参数，再等待未观察的新时间窗口；可另行确认从
  2026-11-04 起的后续完整日期作为前瞻留出，当前不下载或启动该实验。
- validation 选型后冻结候选，最终 test 不再选参；质量不过则停止，不自动 refit。

## 5. 后续实施与授权边界

本轮只交付事件身份修复、独立数据修复对照和上述方案。后续建议顺序：

1. 限定预算核对异常近期日期的上游行数，确定是否存在采集缺口；BigQuery 另行授权。
2. 实现独立 evaluation Artifact，先盘点各层样本量并冻结评估协议。
3. 用修复数据训练同参数基线与候选，再按协议评估；本轮不提前训练。
4. 质量过门禁后才进行最终 refit、Bundle 和 API 验收；激活及部署另行确认。

不把数据正确性通过写成模型质量通过，不提交 / 推送、不改功能总览或 Changelog。
