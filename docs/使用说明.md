# 使用说明

本文档说明如何在单台 Apple Silicon Mac 上运行数据采集、标准化、训练、评估和 ServingBundle 发布。第一版不修改 Starcat 现有服务，也不启动公网 REST API。

## 1. 环境准备

需要 Python 3.12 和 `uv`。Mac mini、MacBook Pro 和 Mac Studio 都可以运行，不要把同一个 `workspace/` 放在多机共享目录同时写入。

```bash
uv sync --all-groups
make check
```

凭据通过环境变量或 Application Default Credentials 提供，不得写入 YAML、日志或 Git。macOS 可以使用 Homebrew 安装 Google Cloud CLI，并把查询项目同时设为 ADC quota project：

```bash
brew install --cask gcloud-cli
gcloud auth login
gcloud auth application-default login
gcloud auth application-default set-quota-project YOUR_GCP_PROJECT_ID
export GITHUB_TOKEN='...'
export STARCAT_SUBJECT_HMAC_KEY='...'
```

没有桌面浏览器时，两个登录命令都可以增加 `--no-launch-browser`，在其他设备打开命令输出的认证链接，再把一次性 verification code 输入终端。不要复制账号密码或访问令牌。

## 2. 运行本地完整示例

示例不访问网络，会完整执行 raw 落地、canonical 转换、数据集构建、五个训练任务、离线评估、Bundle 发布和 Registry 激活。

```bash
make demo
```

成功后的主要产物：

```text
workspace/demo/runs/example-local-v1/
├── raw/
├── canonical/
├── dataset/quality-report.json
├── models/
├── evaluation/validation-metrics.json
└── run-manifest.json

workspace/registry/
├── active.json
└── versions/example-local-v1/
    ├── manifest.json
    ├── checksums.json
    └── recommendations.sqlite
```

Registry 版本不可覆盖。再次运行示例前，应同时修改 `run_id` 和 `publish.model_version`。

## 3. 查询、校验和回滚 Bundle

```bash
uv run starcat-recsys bundle verify \
  workspace/registry/versions/example-local-v1

uv run starcat-recsys bundle query \
  workspace/registry/versions/example-local-v1 \
  --repo-id 1 \
  --repo-id 2 \
  --exclude-repo-id 4 \
  --limit 10

uv run starcat-recsys registry activate workspace/registry example-local-v1
```

多个 `--repo-id` 是客户端提供的 seed repos。查询会累加各 seed 的 item-to-item 分数，排除 seed 自身和显式排除项，最多返回 500 条。

## 4. 使用 GH Archive BigQuery

复制 `configs/example-bigquery.yaml`，至少修改以下字段：

- `run_id` 和 `publish.model_version`：每次正式运行使用新版本。
- `billing_project`：承载 BigQuery 查询任务及免费配额或计费归属的 GCP Project。
- `start_date` / `end_date`：UTC 日分区，首次建议不超过 7 天。
- `maximum_bytes_billed_per_day`：每个分区的硬上限。查询先 dry run，预估值超限时不会发起正式查询。
- `maximum_total_bytes_billed`：当前 WatchEvent 任务的累计预计扫描上限；每个新分区正式查询前再次检查。
- `retry_attempts` / `retry_initial_delay_seconds`：只用于限流、服务不可用和网关超时等瞬时 Google API 错误。
- `bigquery_push_metadata.start_year` / `end_year`：PushEvent 仓库目录的四位年份范围。
- `bigquery_push_metadata.maximum_bytes_billed`：PushEvent 跨年份聚合查询的总扫描硬上限，不与 WatchEvent 每日上限混用。
- `minimum_push_events`：仓库在所选年份内至少出现多少次 PushEvent；它过滤完全不活跃的候选，不是 Star 数。
- `repository_limit`：按行为次数选取的候选仓库数。GitHub API 只为这些仓库补 metadata。
- `maximum_requests`：GitHub API 本次请求的硬上限，应不小于 `repository_limit`。
- `cache_directory`：放在 run 目录之外的 ETag cache，供后续新 run 复用；该目录不进入 Bundle。

```bash
uv run starcat-recsys pipeline run --config configs/my-bigquery.yaml
```

首次采集多年 WatchEvent / PushEvent 时，使用两个独立下载任务，不要把数千个远程分区与训练绑成一次不可恢复任务：

```bash
./scripts/download-watch-events.sh start
./scripts/download-watch-events.sh status
./scripts/download-watch-events.sh logs
./scripts/download-watch-events.sh stop

./scripts/download-push-events.sh start
./scripts/download-push-events.sh status
./scripts/download-push-events.sh logs
./scripts/download-push-events.sh stop
```

脚本使用 `screen` 保持后台会话，并用 `caffeinate -ims` 阻止 macOS 在下载期间自动休眠；它不依赖 `launchd`。启动前会确认 `/Volumes/T0` 是实际挂载卷，若移动硬盘未挂载则直接拒绝运行，防止同名路径落到本机磁盘。默认参数对应当前 `2016-01-01` 至 `2026-08-25` 任务。WatchEvent 使用 `/Volumes/T0/Starcat/bigquery/watch-events-2016-2026`，PushEvent 使用 `/Volumes/T0/Starcat/bigquery/push-events-2016-2026`；两者的 Parquet、checkpoint、日志、PID 和 `screen` session 均独立，可并行运行。

两个脚本启动时及运行期间默认每 1800 秒查询当前 Project 本 UTC 月的 `INFORMATION_SCHEMA.JOBS_BY_PROJECT`，在各自日志中输出 `total_bytes_billed`、1 TiB 占比、剩余额度和查询次数。达到 80% 时警告，达到 90% 时停止对应任务；启动时无法读取额度也会拒绝运行。可通过 `STARCAT_BQ_QUOTA_LOG_INTERVAL_SECONDS`、`STARCAT_BQ_QUOTA_WARNING_PERCENT`、`STARCAT_BQ_QUOTA_STOP_PERCENT` 覆盖。这个统计只覆盖 `STARCAT_BQ_BILLING_PROJECT`；同一 billing account 下其他 Project 的用量仍需查看 Cloud Billing 报表。

本机 Admin Console 通过固定 JSON 契约读取状态和触发生命周期动作：

```bash
./scripts/download-watch-events.sh status --json
./scripts/download-push-events.sh status --json --skip-quota
./scripts/download-watch-events.sh start --json
./scripts/download-watch-events.sh stop --json
./scripts/download-watch-events.sh restart --json
```

`status --json` 不返回真实数据目录或日志路径。WatchEvent 与 PushEvent 共用同一 billing
project，控制台在同一批次中只让第一条状态命令查询额度，第二条使用 `--skip-quota`，再复用
第一条 quota；下载 worker 自身每 1800 秒的额度保护不受影响。

把已有下载结果登记进 Admin Console 的 PostgreSQL Catalog 前，使用以下只读命令生成结构化
快照；Web 固定 Action 会调用相同入口：

```bash
./.venv/bin/starcat-recsys lake inspect-watch-events \
  --workspace /Volumes/T0/Starcat/bigquery/watch-events-2016-2026

./.venv/bin/starcat-recsys lake inspect-push-events \
  --workspace /Volumes/T0/Starcat/bigquery/push-events-2016-2026
```

命令按 checkpoint 的 `start_date` / `end_date` 生成完整日期范围。已完成分区重新校验 footer、
字段顺序、行数和 SHA-256；不存在的预期日期标记为 missing，损坏或摘要不一致的分区标记为
failed。输出不包含真实路径，也不会写 checkpoint、Parquet 或 manifest。

训练管道需要直接复用已经下载的分区时，使用 `local_lake_partitions`，不要再配置
`type: bigquery` 触发重复查询：

```yaml
sources:
  - type: local_lake_partitions
    workspace: /Volumes/T0/Starcat/bigquery/watch-events-2016-2026
    dataset: watch_events
    start_date: "2026-08-01"
    end_date: "2026-08-25"
    verify_checksums: true
```

Connector 以 `download-state.json` 为分区清单，逐日校验文件、Parquet schema、行数和
checksum，只在当前 run 写入外部 Artifact manifest，不复制或改写 Raw。第一次验证建议使用
较短日期范围；`verify_checksums: false` 只适合紧接一次完整 `lake inspect-*` 后的重复实验。

Admin Console 的 SQL Lab 最终调用以下 Trainer CLI：

```bash
./.venv/bin/starcat-recsys bigquery sql-lab-dry-run \
  --sql-file /path/to/query.sql \
  --billing-project YOUR_GCP_PROJECT_ID \
  --location US \
  --maximum-bytes-billed 1073741824

./.venv/bin/starcat-recsys bigquery sql-lab-query \
  --sql-file /path/to/query.sql \
  --billing-project YOUR_GCP_PROJECT_ID \
  --location US \
  --maximum-bytes-billed 1073741824 \
  --expected-sql-sha256 'sha256:<dry-run 返回值>' \
  --maximum-result-rows 200
```

SQL Lab 只允许单条 `SELECT` / `WITH ... SELECT`，引用表必须属于 `githubarchive`。正式查询会
重新 dry run，并校验 SQL hash 与 10 GiB 单次上限；返回最多 200 行、2 MiB。Admin Console
通过 `0600` 临时文件传入 SQL，任务结束后删除，SQL 与结果不进入 PostgreSQL Job Catalog。

任务按天生成 `raw/gh_archive/watch-events-YYYYMMDD.parquet`。GH Archive 历史数据存在少量缺失日表，下载器会为这类日期写入零行 Parquet 并登记 checkpoint，然后继续下一天；billing project 等其他 `NotFound` 错误仍会直接失败。每完成一天就原子更新 `download-state.json`；全部完成后生成 `manifest.json`。使用完全相同的参数和 `run-id` 重跑时，已通过 Parquet footer、固定字段和 SHA-256 校验的分区直接跳过。任务范围或预算发生变化时应使用新的 workspace，系统会拒绝用不同配置误复用旧 checkpoint。

BigQuery Connector 将每个 UTC 日期严格校验为 `YYYYMMDD`，只查询对应的 `githubarchive.day.YYYYMMDD` 显式日表。不能改回 `githubarchive.day.*`：该 dataset 包含 `yesterday` View，通配查询会被 BigQuery 以 `Views cannot be queried through prefix` 拒绝。查询只取 WatchEvent 的 event ID、actor ID、repo ID 和事件时间。GitHub Connector 只读取 Repository metadata，不批量拉取 stargazer 列表。

精简 PushEvent 原始下载使用相同日表策略，但落入 `raw/gh_archive_push_events/push-events-YYYYMMDD.parquet`，只保留后续仓库活跃度和协同信号可能用到的五个字段，不下载 `payload` 或 commits：

| 字段 | 含义 |
|---|---|
| `source_record_id` | GH Archive event ID |
| `actor_id` | GitHub actor ID，保持为字符串 |
| `repo_id` | GitHub 稳定仓库 ID |
| `full_name` | 事件发生时观察到的 `owner/repo` |
| `created_at` | PushEvent 发生时间 |

对应单日 SQL 为：

```sql
SELECT
  CAST(id AS STRING) AS source_record_id,
  CAST(actor.id AS STRING) AS actor_id,
  CAST(repo.id AS INT64) AS repo_id,
  repo.name AS full_name,
  created_at
FROM `githubarchive.day.YYYYMMDD`
WHERE type = 'PushEvent'
  AND actor.id IS NOT NULL
  AND repo.id IS NOT NULL
  AND repo.name IS NOT NULL
```

另一条 `BigQueryPushEventMetadataSource` 是面向 canonical 仓库目录的聚合查询，不替代上述原始日分区。它查询 `githubarchive.year.*`，先在 BigQuery 内按 `repo.id` 聚合，再只把仓库目录下载到本机。它输出：

| 字段 | 含义 |
|---|---|
| `repo_id` | GitHub 稳定仓库 ID |
| `full_name` | 所选年份范围内最后一次 PushEvent 观察到的仓库名 |
| `first_push_at` | 所选范围内第一次观察到 PushEvent 的时间，不是权威创建时间 |
| `last_push_at` | 所选范围内最后一次观察到 PushEvent 的时间，不是 GitHub 当前状态保证 |
| `push_event_count` | 所选范围内 PushEvent 数量 |
| `fetched_at` | BigQuery 查询执行时间 |

实际 SQL 为：

```sql
WITH push_events AS (
  SELECT
    CAST(repo.id AS INT64) AS repo_id,
    repo.name AS full_name,
    created_at
  FROM `githubarchive.year.*`
  WHERE _TABLE_SUFFIX BETWEEN '2016' AND '2025'
    AND type = 'PushEvent'
    AND repo.id IS NOT NULL
    AND repo.name IS NOT NULL
),
repository_timeline AS (
  SELECT
    repo_id,
    ARRAY_AGG(full_name ORDER BY created_at DESC, full_name DESC LIMIT 1)[OFFSET(0)]
      AS full_name,
    MIN(created_at) AS first_push_at,
    MAX(created_at) AS last_push_at,
    COUNT(*) AS push_event_count
  FROM push_events
  GROUP BY repo_id
  HAVING COUNT(*) >= 1
)
SELECT
  repo_id,
  full_name,
  first_push_at,
  last_push_at,
  push_event_count,
  CURRENT_TIMESTAMP() AS fetched_at
FROM repository_timeline
ORDER BY repo_id
```

2026-08-26 已使用 GCP CLI 对上述 2016～2025 SQL 做真实 dry run：语法和输出 schema 均通过，精确预计扫描 `540643059637` bytes，`totalBytesBilled=0`。这约为 503.6 GiB，低于按需查询每月前 1 TiB 的免费额度，但免费额度由同一计费账号当月其它查询共享；代码仍要求显式配置 `600000000000` bytes 上限。此次只做 dry run，没有执行这条大查询，也没有生成实际 2.5M 级仓库产物。

数据进入 canonical 后，PushEvent 只作为低精度基础 metadata。延迟 GitHub API 会按 WatchEvent/Starcat 行为量选择 Top N 仓库，并覆盖当前名称、描述、Topics、语言、License、Star/Fork 数及仓库状态。这样既避免数百万次 API 调用，也不会把历史 Push 观察值伪装成当前 GitHub 状态。

2026-08-23 的生产链路验证使用未绑定结算账号、已启用 BigQuery API 的项目执行：`20240101` 日表 dry run 为 `191450481` bytes，带 `200000000` bytes 硬上限的正式查询返回 `131766` 行。该结果证明 ADC、每日预算门禁、查询执行和 Arrow 转换可用；它不是未来日期范围的固定容量估算，正式采集仍必须逐日 dry run。

2026-08-26 对 WatchEvent `2016-01-01`～`2026-08-25` 做了全范围 dry run：2016～2025 使用静态年度表，2026 使用 237 个明确日表，合计预计扫描 `524507021732` bytes（约 `0.477 TiB`），`totalBytesBilled=0`。这只是查询计划估算，不包含事件行数和最终 Parquet 大小；正式下载仍逐日执行并受 1 GiB 每日上限、600 GB 累计上限和未启用 Billing 的项目边界共同保护。

外部依据：[GitHub REST API Versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions) 确认当前配置使用 `2026-03-10`；[BigQuery Estimate and control costs](https://cloud.google.com/bigquery/docs/best-practices-costs) 说明 dry run 和 `maximum_bytes_billed` 的费用门禁；[BigQuery pricing](https://cloud.google.com/bigquery/pricing) 说明按需查询每月前 1 TiB 免费。

## 5. 导入 Starcat 匿名快照

YAML 中的数据源配置：

```yaml
sources:
  - type: starcat_snapshot
    paths:
      - ../landing/snapshot-001.json
      - ../landing/snapshot-002.json
    subject_hmac_key_env: STARCAT_SUBJECT_HMAC_KEY
    maximum_repositories_per_snapshot: 100000
  - type: github_api
    repo_ids_from_canonical: true
    repository_limit: 5000
    maximum_requests: 5000
```

快照必须符合 Starcat schema v1：

```json
{
  "schema_version": 1,
  "snapshot_id": "0191f9e3-95d4-7f52-b4d3-28d628e3a02b",
  "participant_id": "63b7d101-88c0-4cee-859f-c61f64d8db96",
  "captured_at": "2026-08-22T08:30:00Z",
  "mode": "full",
  "content_hash": "sha256:...",
  "repositories": [
    {"repo_id": 1342004, "starred_at": null},
    {"repo_id": 41881900, "starred_at": "2023-06-11T13:20:10Z"}
  ]
}
```

`repositories` 必须按 `repo_id` 升序、不重复，`mode` 固定为 `full`。`content_hash` 是对不包含 `content_hash` 本身的 canonical JSON 做 SHA-256，可用项目中的 `snapshot_content_hash` 生成。Connector 验证成功后立即将 `participant_id` 转换为 HMAC 标识，canonical、dataset、model 和 Bundle 中都不保留原值。

## 6. 从 starcat-collection-api 拉取

设置只对当前 shell 可见的 Admin Key，不要写入 YAML：

```bash
export STARCAT_COLLECTION_ADMIN_KEY='...'
export GITHUB_TOKEN='...'
uv run starcat-recsys pipeline run --config configs/example-collection.yaml
```

`starcat_collection_api` 配置：

```yaml
sources:
  - type: starcat_collection_api
    base_url: http://127.0.0.1:5011
    admin_key_env: STARCAT_COLLECTION_ADMIN_KEY
    timeout_seconds: 60
    maximum_snapshots: 100000
    maximum_repositories_per_snapshot: 100000
    maximum_response_bytes: 536870912
```

Connector 主动请求 `/internal/v1/training/recommendation-snapshots/export`，必须同时验证
HTTP 成功状态与 `X-Starcat-Export-Checksum`。它拒绝超限响应、未知字段、原始
`participant_id`、重复 active subject、无序 repo ID 和非法时间。落地的
`raw/starcat_collection_api/snapshots.jsonl` 只包含已 HMAC 的 `source_subject_id`，之后直接复用
Starcat 快照 canonical 逻辑。

`configs/example-collection.yaml` 还会从 canonical 仓库 ID 延迟拉取 GitHub 公开 metadata。
本地只验证 Collection 数据链路时，可把该 `github_api` 源换成已落地的
`local_file` metadata fixture，避免访问 GitHub。

仓库已提供 `configs/example-collection-local.yaml` 作为三仓本机 E2E 配置。它从真实
Collection Admin 导出拉取 Star 快照，同时复用 `examples/data/github-repositories.jsonl`
补齐 1～4 号公开仓 metadata，因此不需要 `GITHUB_TOKEN`：

```bash
export STARCAT_COLLECTION_ADMIN_KEY='admin-e2e-key'
uv run starcat-recsys pipeline run --config configs/example-collection-local.yaml
uv run starcat-recsys bundle verify \
  workspace/registry-e2e/versions/example-collection-local-v1
uv run starcat-recsys bundle query \
  workspace/registry-e2e/versions/example-collection-local-v1 \
  --repo-id 1 --limit 3
```

示例版本不可覆盖；再次执行前应复制配置并同时修改 `run_id`、`workspace`、`registry`
和 `publish.model_version`。完整的服务启动与 Starcat live test 命令见 Starcat 专项文档
`docs/2-产品/需求讨论/推荐算法/Starcat公开Star数据贡献使用说明.md`。

## 7. YAML 配置说明

| 区域 | 主要字段 | 说明 |
|---|---|---|
| 根节点 | `run_id` / `workspace` / `registry` / `random_seed` | 运行身份、工作区、Registry 和随机种子 |
| `sources[]` | `type` | `bigquery` / `local_lake_partitions` / `github_api` / `starcat_snapshot` / `starcat_collection_api` / `local_file` |
| `dataset` | `train_end` / `validation_end` | UTC 时间切分；缺少 `starred_at` 的旧快照只进 train |
| `dataset` | `minimum_repository_interactions` | 仓库在 `train_end` 前至少被多少个去重后的来源内主体正向关联；BigQuery 下近似训练窗口内可见 Star 支持度，不是当前 Star 总数 |
| `dataset` | `minimum_repositories_per_subject` / `maximum_repositories_per_subject` | 主体有效仓库数上下限；大规模 BigQuery 示例使用 10～800 |
| `training` | `top_k` / `svd_components` | Popular、SVD 和 co-star 共用的核心配置 |
| `training` | `half_life_days` / `legacy_time_weight` / `shrinkage` | co-star 时间衰减和平滑 |
| `training` | `reference_time` | 必须与 `dataset.train_end` 表示同一时刻，否则拒绝运行 |
| `training` | `maximum_repositories_per_subject` | 限制单主体 pair 组合数 |
| `training` | `run_ablations` | 同时训练 no-decay 和 no-shrinkage 变体 |
| `evaluation` | `split` / `k` | `validation` 或 `test`，输出 Recall/NDCG/MRR/Coverage |
| `publish` | `model_version` / `selected_model` | 待发布版本和冠军模型 |
| `publish` | `metric_gates` | 指标小于门限时拒绝发布 |
| `publish.recommend_api` | `base_url` / `publish_key_env` | 可选；把本地 Bundle 发布到统一 Recommend API |
| `publish.recommend_api` | `timeout_seconds` / `maximum_bundle_bytes` / `activate` | 发布超时、压缩包上限和是否立即激活 |

配置文件内容会计算 SHA-256，写入每层 manifest 和最终 Bundle。

## 8. 数据质量和评估

`dataset/quality-report.json` 记录 raw interaction 数、最新快照保留数、同源记录去重数、唯一 subject-repo 数、公开仓库过滤数、评估保留主体数、训练合格主体数、各时间切分数和缺少时间的数量。训练数据中的 `training_eligible` 只由 train cutoff 前的 repo 数决定；三个训练器都拒绝读取 validation/test 或训练资格无效的行。

`evaluation/*-metrics.json` 对 Popular、SVD、co-star 和两个 ablation 变体使用同一时间留出集评估。Coverage 只以训练 catalog 为分母。离线结果不等同于 Starcat 端上效果，正式切换仍需要小流量或人工验收。

当训练数据只有一个合格主体，`run-manifest.json` 会把 `train:svd` 标记为 `skipped`，并在 `detail` 保存“至少需要 2 个主体”的原因；这属于冷启动降级，不是整次运行失败。配置选择 `costar` 或 `popular` 时仍可正常生成并发布 Bundle。其它异常不会被静默跳过。

## 9. Starcat 和 REST API 如何使用产物

ServingBundle 包含：

- `recommendations.sqlite`：公开 repo metadata 和预计算 item-to-item Top-K。
- `manifest.json`：模型版本、Git commit、配置 hash、随机种子、输入 checksum 和离线指标。
- `checksums.json`：Bundle 内文件校验值。

配置 `publish.recommend_api` 后，管道会在本地 Registry 安装成功后执行第二个 Publisher：只打包上述三个文件，使用 `STARCAT_RECOMMEND_PUBLISH_KEY` 调用 `starcat-recommend-api /internal/v1/model-bundles/{version}?activate=true`。服务端成功响应后，Trainer 在本次 run 下写入不含密钥的 delivery receipt。

```bash
export STARCAT_RECOMMEND_PUBLISH_KEY='仅在当前 shell 中设置'
uv run starcat-recsys pipeline run --config configs/example-collection-local.yaml
```

Starcat 通过 `starcat-recommend-api /api/v2` 查询同一 Bundle。在线 API 不得读取 raw、canonical 或 dataset，也不接收 `participant_id`；`/api/v1` SimRepo 接口不受这条交付链路影响。

## 10. 故障处理

| 错误 | 处理 |
|---|---|
| `BigQuery ... 超过上限` | 缩小日期范围或在确认费用后显式调整单日预算 |
| `Views cannot be queried through prefix` | 当前版本应使用显式日表；出现该错误说明仍在运行旧版 `day.*` 查询 |
| ADC 提示 quota project 缺失 | 执行 `gcloud auth application-default set-quota-project YOUR_GCP_PROJECT_ID` |
| `GITHUB_TOKEN 未配置` | 只在当前 shell 设置 token，不要写入 YAML |
| `GitHub API 限流` | 根据 `remaining/reset` 等待限额恢复，ETag cache 在重跑时复用 |
| `content_hash 校验失败` | 重新对排序后 canonical snapshot 计算 hash |
| `Collection 导出 checksum 校验失败` | 不使用本次 raw 产物；检查代理截断、服务日志和 Admin Key 目标 |
| `模型版本已存在` | 使用新 `run_id` 和 `model_version`；Registry 禁止覆盖 |
| `指标门禁未通过` | 保留运行用于分析，修正后使用新版本重训 |
| Bundle checksum / quick_check 失败 | 禁止激活，回滚到上一个已校验版本 |
| `Recommend API Bundle 发布失败` | 本地 Registry 产物仍有效；检查 Publish Key、服务地址和 Bundle 上限后用新 run/version 重试 |

## 11. 多机扩展边界

当前可执行实现是 `LocalExecutor`，一次 run 在一台机器上串行编排。Source、Normalizer、DatasetBuilder、Trainer、Evaluator 和 Publisher 都以 `Artifact URI + checksum + manifest` 交换数据，不依赖共享 Python 内存。后续可以用远程 `TaskExecutor`、对象存储和任务租约将不同节点分配到多台 Mac，而不改写核心训练接口。第一版不实现跨 Mac MPS 同步梯度训练。
